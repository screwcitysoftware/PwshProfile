# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Working in this repo

**Start every task in plan mode.** Explore the code and present a plan for approval before making edits — the session defaults to plan mode (`defaultMode` in `.claude/settings.local.json`). For a **trivial change** (a typo, a one-line doc tweak, a rename), proactively tell the user they can bypass the full workflow — accept the plan immediately, or toggle plan mode off — rather than walking the whole plan/explore/design loop for something that doesn't need it.

## What this is

A PowerShell (pwsh) module holding the reusable building blocks of the user's profile. It is imported (via the `.psd1` manifest) at the top of `Microsoft.PowerShell_profile.ps1`, and its exported functions drive profile startup. There is no build step or linter config. The README documents each exported function's behavior — read it before changing a function, and update it when behavior changes.

The name nods to "Screw City", a nickname for Rockford, Illinois (a historic screw/fastener/machine-tool manufacturing hub). Rockford is *also* the "Forest City", and the module ships two bundled oh-my-posh themes that lean into that dual identity: `screwcity` (purple/blue, signature `#c9aaff`, 🔩 `:nut_and_bolt:` step icon, "Screw City" display name) and `forestcity` (green/brown/gray, signature `#8fce72`, 🌳 `:deciduous_tree:` step icon, "Forest City" display name). Each theme carries a matching **display name, banner color, step icon, bat `BatTheme`, fd `LsColors`, and fzf `FzfColors`**, resolved through `Private/Prompt/Get-BundledThemeBranding.ps1`; a custom theme falls back to the neutral `screwcity` branding. The banner **text** is *not* theme-specific — it defaults uniformly to `$env:COMPUTERNAME` (the machine name) for every theme, custom included.

## Development

Reload after changes:

```powershell
Import-Module ./ScrewCitySoftware.PwshProfile.psd1 -Force
```

Run the checks the way CI does (Pester 5 + PSScriptAnalyzer; `build.ps1 -Task Bootstrap`
installs them if missing) — this lints **and** runs the Pester suite under
`Set-StrictMode -Version Latest`, so a clean local run matches a clean CI run. Run it in a **clean**
PowerShell session (`-NoProfile`, like CI) so the profile's own loaded module / global state can't
mask a failure:

```powershell
pwsh -NoProfile -NoLogo -Command "& .\build.ps1 -Task Analyze, Test"
```

For a quicker inner loop you can call Pester directly, but note it skips PSScriptAnalyzer and
does **not** set StrictMode — so it can hide failures CI catches (e.g. reads of unset
variables, lint findings). Confirm with `build.ps1` before pushing:

```powershell
Invoke-Pester -Path ./Tests
```

For console-rendering changes (`Invoke-Step`), also eyeball the output in a fresh `pwsh -NoProfile` session with the module imported (e.g. `Invoke-Step "x" { Start-Sleep -Milliseconds 50 }`) — the Spectre spinner only renders in an interactive console, so tests can't see it (they mock the Spectre cmdlets instead).

**After every code change, check `README.md` for documentation that needs updating** — it's the source of truth users read via `Show-PwshProfileReadme`, and it drifts easily. Review (and update where the change touches them): the affected function's `### ` section, parameter bullets, and examples; the **Layout** file tree (`Public/`/`Private/` listings) when files are added/removed/renamed; the `FunctionsToExport` list in the `.psd1`; the Installation/Usage walkthroughs; and any cross-references or counts (e.g. the bundled-font count). The module-level test only enforces that each exported function has *a* README section plus comment-based help — it does **not** verify the prose is current, so keeping it accurate is on you. Also update the function's comment-based help in the same change.

## Architecture

**Standard Public/Private layout, grouped into feature subfolders.** One exported function per file under `Public/`, file named exactly after the function (`Verb-Noun.ps1`). Both `Public/` and `Private/` are organized into parallel feature subfolders — `Install/`, `Startup/`, `Prompt/`, `Tools/` (tool *and* completion enablers), `Rendering/`, `Docs/`, `Core/` — and a function lives in the subfolder matching its responsibility. The `.psm1` is a generic loader (recursively dot-sources `Public/**/*.ps1` and `Private/**/*.ps1` if present, exports public base names) — it never needs editing. **Subfolder nesting is purely organizational: it never affects which functions are exported.** The manifest carries an explicit *flat* `FunctionsToExport` list, and the module-level test globs `Public/` recursively. Adding a function requires three touches: the new `Public/<area>/Verb-Noun.ps1`, its name in `FunctionsToExport` in the `.psd1`, and a README section. Internal helpers go in the matching `Private/<area>/` subfolder. A module-level test enforces that Public file names (across all subfolders), manifest exports, and actual exports all match, and that every function has comment-based help. **One deliberate exception:** `Public/Tools/Select-Fzf.ps1` bundles its private `Invoke-FzfRaw` fzf-invocation seam *in the same file* (not in `Private/`) so `Select-Fzf` stays a single portable unit; `Invoke-FzfRaw` is still internal (the loader exports only Public *file* base names and it isn't in the manifest), and it's a real function rather than an inline call so the mapping logic stays unit-testable (Pester can't mock a native `fzf.exe` invocation).

**`Invoke-Step` nesting protocol** — the invariant everything else renders through. `Public/Rendering/Invoke-Step.ps1` is the dispatcher (module-scoped state is declared at the top of that file, outside the function, initialized once at import); the per-step worker lives in `Private/Rendering/Invoke-StepInternal.ps1`.
- The invariant: the top-level `Invoke-Step` call opens the transient status spinner (`Invoke-SpectreCommandWithStatus`) and stashes its `[Spectre.Console.StatusContext]` in `$script:StepStatusContext`; nested calls see the context and only push/pop the `$script:StepPath` breadcrumb stack, updating `$ctx.Status` to the joined path (prefixed by `$script:StepRootIcon`, the top-level step's icon). The spinner clears itself when the top-level scriptblock returns, and the dispatcher then writes one permanent summary line (`Write-SpectreHost`, dotted leader + `[  NNms]` total elapsed). Nested substeps leave no scrollback output; a throwing step writes no summary (state is still restored in `finally`).
- The step icon value carries **no trailing space** (e.g. `:nut_and_bolt:`, not `:nut_and_bolt: `). The single separator between the glyph and the step text is added at every render site (the spinner label, the summary line, and the breadcrumb) via `Private/Rendering/Get-StepIconPrefix.ps1`, which `TrimEnd`s the icon and appends one space (and returns `''` for an empty icon, so no stray leading space). It's idempotent, so a legacy `:nut_and_bolt: ` baked into someone's `$PROFILE` still renders with one space. When adding a render path that prints the icon, go through `Get-StepIconPrefix` rather than concatenating the raw value.
- The scriptblock handed to `Invoke-SpectreCommandWithStatus` must stay a plain literal — `.GetNewClosure()` rebinds `$script:` writes to a throwaway dynamic module and silently breaks the context stash — and its result must be swallowed (`$null =`) because the status helper emits `$null` even for a void scriptblock.
- If PwshSpectreConsole is unavailable (`Get-Command` guard), the step body still runs, silently and unrendered — failure tolerance, not a renderer.
- Anything that writes to the console mid-step (stray `Write-Host` or external-command stdout inside a step body) tears the live spinner — route output through nested `Invoke-Step` calls or suppress it (`*> $null`). `Write-Warning` stays the failure-reporting channel and is handled specially: the top-level dispatcher redirects the body's warning stream (`3>&1`, filtered to `[WarningRecord]`) into the module-scoped `$script:StepWarnings` list instead of letting it paint into the live spinner, then **replays** the captured warnings via `Write-Warning` in a `finally` after the spinner has cleared and the summary line is written. So warnings no longer tear the render *and* no longer vanish — they persist in scrollback, grouped under the top-level step's summary line (even if the step threw). A warning surfacing *after* its summary line, rather than inline, is by design.

**`Enable-*` pattern** (Enable-OhMyPosh, Enable-Zoxide, Enable-Fzf, Enable-FastNodeManager, Enable-Xh, Enable-Jq, Enable-Bat, Enable-Fd, Enable-Ripgrep, Enable-Less, Enable-Lazygit, Enable-Uv): each tool enabler runs two nested substeps, `Invoke-Step "Install"` and `Invoke-Step "Initialize"`, so they render as indented timed lines under the caller's step. Some enablers self-register their own tab completion *inline* in their Initialize substep (Enable-Xh via `xh --generate complete-powershell`, Enable-Bat via `bat --completion ps1`, Enable-Fd via `fd --gen-completions powershell`, Enable-Ripgrep via `rg --generate complete-powershell` — note ripgrep and fd spell the flag differently, and Enable-Uv via `uvx --generate-shell-completion powershell`) — that completer is theirs and rides along whenever the tool is enabled (the tool's own `-Enable` token), distinct from the external-CLI **Completion enablers** below. Where an enabler also *aliases* its tool over a builtin, it extends the generated completer's `-CommandName` to cover the alias too (PowerShell completers don't follow aliases): Enable-Xh always adds `http`/`https` (to `xh`/`xhs`), and Enable-Bat adds `cat` only under `-ReplaceCat` (the alias's completion is meaningless when `cat` is still `Get-Content`). Each `-replace` is coupled to the tool's exact `-CommandName 'xh'`/`'xhs'`/`'bat'` literal — a re-quoting in a future build silently drops only the alias's completion. (Enable-Jq and Enable-Less are install-mostly: jq has no Initialize work at all, and less only sets `$env:LESS` (and, under `-ReplaceMore`, `$env:PAGER` + a `more`→`less` alias) — GNU less ships no PowerShell completer and has no fzf/fd-style palette, so it registers no completion and isn't themed.) (**Enable-Uv is the one enabler that deliberately *declines* a completer its tool offers.** uv ships three exes and would need a registration per command name, since a completer binds to a name and doesn't follow a sibling. Only `uvx` is registered: `uv`'s own completer is ~754 KB of generated PowerShell costing **~244ms of every startup** to produce and parse — measured 141ms generate + 103ms `Invoke-InGlobalScope`, versus ~49ms for uvx and ~42ms for ripgrep — which made it the most expensive single step in the profile, about a quarter of the whole WinGet section. The trade-off is knowingly the wrong-way-round one, since `uv` is typed more than `uvx`; it was taken for the startup budget. `uvw` is uncompleted too. If you ever add uv's back, mind the asymmetry: uv spells the request as a *subcommand* (`uv generate-shell-completion powershell`), uvx as a *flag*. `Tests/Enable-Uv.Tests.ps1` pins the omission so it can't drift back silently.) (Enable-Fzf is the exception that needs more than self-completion: fzf ships no PowerShell key bindings, so its Initialize installs the **PSFzf** module via `Import-ModuleSafe` and calls `Set-PsFzfOption` to bind Ctrl+T/Ctrl+R, enable fd traversal, and register the Ctrl+G git chords — see the orchestrator notes below.)
- Install: the per-tool `Invoke-Step "Install"` body is a single call to the shared `Private/Tools/Install-WingetPackageSafe.ps1` helper (the install logic is identical across the tool enablers, so it lives in one place — pass `-Id`, `-Exe`, `-CallerName`, plus optional `-PathDir` and `-Scope` (`user`/`machine`)). `-PathDir` defaults (inside the body, *after* the already-installed short-circuit, so a present tool never builds it) to the winget portable Links dir `$env:LOCALAPPDATA\Microsoft\WinGet\Links`, which every portable enabler (zoxide/fnm/fzf/xh/jq/bat/fd/ripgrep/less/lazygit/uv) shares — the two full-installer packages pass an explicit `-PathDir`: oh-my-posh (`Programs\oh-my-posh\bin`, `-Scope user`) and git (`$env:ProgramFiles\Git\cmd`; no `-Scope`, so winget's machine default — a machine install may need elevation, tolerated as a warning). That helper installs via the first-party **`Microsoft.WinGet.Client`** module (`Install-WinGetPackage -Id <id> -Source winget -MatchOption Equals -Mode Silent [-Scope User|System]`), loaded on demand through `Import-ModuleSafe`. Crucially the already-on-PATH short-circuit (`Get-Command <Exe>`) runs **before** the module import, so an already-installed tool never loads `Microsoft.WinGet.Client` — only a first-time/missing install pays that cost (the reason package installs were moved off the startup-only `winget.exe` shell-out is acceptable). The `Install-WinGetPackage` call is wrapped in `$ProgressPreference = 'SilentlyContinue'` (restored in `finally`) so its progress bar doesn't tear `Invoke-Step`'s live Spectre spinner. After installing it patches the *current session's* `$env:Path` with the resolved `-PathDir` so the install is usable immediately (winget — CLI or cmdlet — only updates the registry user PATH, not the live process). Finally it re-checks `Get-Command <Exe>`; if the exe still isn't resolvable, `Write-Warning` surfacing the result `.Status`/`.InstallerErrorCode`. The post-install `Get-Command` re-check is the success signal — not the result code, which can be benign non-zero. The `($env:Path -split ';') -notcontains $PathDir` guard before appending PATH is deliberate — without it `$env:Path` grows on every profile reload (split-and-compare, not `-like`, so `[`/`*` in a path aren't treated as wildcards).
- Initialize: guarded by `Get-Command`, so a failed install degrades (after the Install step's warning) and startup continues.
- Initialize must run the tool's init/completion output through `Invoke-InGlobalScope (... | Out-String)`, never a bare `Invoke-Expression`. A module function that `Invoke-Expression`s the init text tags every function/alias it defines with the module's name — even `function global:` ones — so they leak into `Get-Command -Module ScrewCitySoftware.PwshProfile`. `Invoke-InGlobalScope` executes the script against the engine's top-level session state, so the helpers land in the true global scope, unattributed, exactly as if run at the prompt.
- New tool enablers should follow this exact shape. `Enable-FastNodeManager` auto-switches the node version on directory change by registering a `LocationChangedAction` hook (PowerShell 6.2+) — run in global scope via `Invoke-InGlobalScope`, chaining any existing handler and guarded by `$global:__fnm_loc_hooked` so a reload doesn't stack it. The hook gates the spawn: it walks up for the files fnm reads (`.nvmrc`, `.node-version`, `package.json`, ~3ms) stamps each with its write time, and only runs `fnm use --silent-if-unchanged` (~41ms) when that **stamp changes**. Comparing the stamp rather than merely testing for a version file matters three ways: fnm reverts to the default on the way *out* of a project; the write time catches an in-place edit that a path comparison would miss; and stamping the whole chain catches an edit to a `.nvmrc` that a nearer `package.json` would otherwise shadow. Because `LocationChangedAction` fires on *any* location change (`cd`/`z`/`Set-Location`/`Push-Location`/`..`), this is independent of zoxide and of call order — there's no longer a "call after `Enable-Zoxide`" requirement (the old `__zoxide_cd` wrap is gone). `Enable-Zoxide` registers its *own* `LocationChangedAction` the same way (guarded by `$global:__zoxide_loc_hooked`, running `zoxide add` for filesystem locations — `zoxide init … --hook none` skips zoxide's default prompt wrapper, which oh-my-posh's prompt-module remove/re-add silently clobbers on reload). The two hooks compose: each captures the other (or `$null`) as its base and chains, and since `Enable-Zoxide` runs before `Enable-FastNodeManager`, zoxide is the base of fnm's wrapper. oh-my-posh remains the only thing that hooks the prompt.

**Completion enablers** — one public `Enable-<Tool>Completion` per CLI, all living under `Public/Tools/Completions/` (currently `Enable-WingetCompletion`, `Enable-AzureCliCompletion`, `Enable-TailscaleCompletion`, `Enable-DockerCompletion`, `Enable-1PasswordCompletion`, `Enable-GithubCliCompletion`). Unlike the `Enable-*` tool enablers, these only *register* tab completion — no Install/Initialize substeps — and open no `Invoke-Step` of their own; the orchestrator's Completions step (nested under **Core**) supplies the label (e.g. `Invoke-Step "Tailscale Completions" { Enable-TailscaleCompletion }`). Each guards on its tool (`Get-Command`) so a missing CLI is a silent no-op. The registration mechanism varies by tool: winget uses a native `winget complete` argument completer; `az` is a Python/argcomplete CLI driven via temp-file + `_ARGCOMPLETE`/`COMP_*` env vars (there is **no** `az completion powershell`); `tailscale`, `op`, and `gh` are Cobra CLIs that share the **module-private** `Private/Tools/Completions/Register-CobraCompletion.ps1` engine (generates `<cmd> completion powershell` and activates it via `Invoke-InGlobalScope`, run in global scope so its helper functions/filters stay reachable at tab time and aren't tagged to the module). `tailscale`/`op` take the shell positionally; `gh` is the exception — it requires the flag form `gh completion -s powershell` (a bare positional `powershell` makes gh emit **bash**), so `Enable-GithubCliCompletion` overrides the engine's default via `Register-CobraCompletion`'s `-CompletionArgument` parameter (defaults to `@('completion','powershell')`); Docker has no built-in completion so `Enable-DockerCompletion` imports the community `DockerCompletion` module via `Import-ModuleSafe`. New completions follow this shape — a public `Enable-<Tool>Completion` in `Public/Tools/Completions/`, keeping the gnarly per-tool registration in its own function (reusing `Register-CobraCompletion` for Cobra CLIs), never inline in the orchestrator.

**Orchestrator contract** (`Initialize-PwshProfile`): startup is the banner plus two top-level sections — **Core** and **WinGet** — split by install model (WinGet = the CLIs installed via WinGet; Core = everything else). **Every tool always runs** — there is no `-Enable`/`-EnableAll` and no selection to resolve; the parameters configure how each tool is *wired*, not whether it is present. `Install-PwshProfile` installs the winget CLIs during setup, so at startup each `Enable-*` `Invoke-Step "Install"` short-circuits on `Get-Command` and costs ~0ms; a tool that is genuinely missing (a fresh machine, or one added by a later module version) is installed at startup instead — the accepted consequence of dropping the pin. Both sections always render. The **tool set is one source of truth** — `Private/Startup/Get-PwshProfileToolCatalog.ps1` returns the ordered **Core / WinGet** → `{Label;Token;Install;Help}` map (each entry's `Install` kind is `winget`/`module`/`none`; the **WinGet group is *derived* as `Install -eq 'winget'`**, so the rule can't drift); `-Token` gives the flat list, and a `winget` row also carries **`PackageId` and `Exe`** — the same pair its `Enable-*` passes to `Install-WingetPackageSafe` — which is what lets `Install-PwshProfile` install the whole set up front. Every row declares both even when `$null` (StrictMode). It also carries **`PathDir`/`Scope`** — `$null` for the portables, which take `Install-WingetPackageSafe`'s shared Links default, and real values for the two full installers (`git` → `%ProgramFiles%\Git\cmd`, no scope; `oh-my-posh` → `%LOCALAPPDATA%\Programs\oh-my-posh\bin`, `-Scope user`). Those columns are exactly what let git and oh-my-posh *be* in the catalog: without them `Install-PwshProfile` would install the package correctly and then append the shared Links dir to `$env:Path`, so the post-install re-check would warn about an install that had in fact worked. **The grouping is by install MODEL, not by the startup section a feature renders under** — git and oh-my-posh are winget rows and group as WinGet, while the orchestrator deliberately runs them in **Core** (git first, so it is on PATH for posh-git and the git-aware WinGet tools). **`Tests/ToolCatalog.Tests.ps1` reads each `Enable-*` source and asserts the catalog's `PackageId`/`Exe` appear in it** — the replacement for the catalog↔`ValidateSet` anti-drift check lost with `-Enable`, and stronger than it was, since a mismatch would otherwise have setup install one package and the first shell install another. Token→function is by convention (`Enable-<Token>`) with one exception the test hardcodes: `Fnm`→`Enable-FastNodeManager`; the file is **searched recursively under `Public/`**, not joined onto `Public/Tools`, because `Enable-OhMyPosh` lives in `Public/Prompt`. A second check pins **`PathDir`/`Scope`**, and it cannot compare literals the way `PackageId` does — the enabler builds the path with `Join-Path` against an environment variable — so it lifts the argument *expression* out of the enabler's own AST and evaluates it (a bare word like `-Scope user` parses as a `ConstantExpressionAst` and is read as a value, since evaluating its text as script would try to *run* it). Adding a tool means a catalog entry + an `Invoke-Step` line in the orchestrator + the usual Public/manifest/README touches; the package metadata is now enforced, the orchestration line still is not. `Tests/ToolCatalog.Tests.ps1` keeps a tripwire asserting `-Enable`/`-EnableAll` have not been reintroduced. **git (`Enable-Git`, `Git.Git`) and oh-my-posh are catalog rows** (they were outside it until the inventory needed to show the full list); only the `which` alias remains outside, since it installs nothing. git still runs first in **Core** so it's on PATH for posh-git and the WinGet-section tools that lean on it (PSFzf git chords, lazygit). The shell completions (winget/Azure CLI/Tailscale/Docker/1Password/GitHub CLI — registration only; they detect external CLIs and install nothing) live in **Core**. There are **no `-Skip`/`-SkipSection` parameters** — they were removed. **Retired parameters are absorbed, not rejected**: a `[Parameter(ValueFromRemainingArguments)] [object[]]$LegacyArgument` catches anything the binder can't match, and the body warns and continues. This exists because removing `-Enable`/`-EnableAll` broke *every* profile ever generated — the old Build always emitted a tool pin — and a `ParameterBindingException` fires **before the body runs**, so those shells got no banner, no prompt, no tools, nothing. That is the "never throw out of profile startup" rule failing at the one place it matters most. Two messages, because the causes need different fixes: a name in `$script:RetiredParameter` (file top, outside the function, the `Invoke-Step` module-state shape — **add to it when you retire a parameter**) says "your block is stale, run `Install-PwshProfile`"; anything else is reported as a possible typo. **The guard is `$null -ne $LegacyArgument`, never `.Count`** — with no remaining arguments the variable is `$null`, and `$null.Count` *throws* under `Set-StrictMode -Version Latest`, which is how the suite and CI run, so the obvious check would make the shim the very thing it prevents (`@($null).Count` is `1`, so that is no use either). Verified: the flag and its value are absorbed together, so a typo's value cannot land on the positional `-BannerText`, and valid parameters still bind alongside a retired one. A `-Setting <hashtable>` bag — one stable parameter carrying the settings as data, so the call shape never changes again — was considered and deferred; the catch-all already covers a *removed* parameter, but a *renamed* one still loses its value (it reverts to the default until the user re-runs setup), and there is nowhere to put a schema-version stamp without the bag. The theme is chosen via two mutually-exclusive parameter sets — `Bundled` (`-Theme <name>`, default `screwcity`, via `Get-BundledThemePath`) and `Custom` (`-CustomTheme <path>`) — both forwarded to `Enable-OhMyPosh -Configuration`. Banner: `-BannerText` carries a real default of `$env:COMPUTERNAME` for **every** theme and is `[ValidateNotNullOrEmpty()]` (it can't be empty); to render **no** banner use the `-NoBanner` switch (the banner block is guarded `if (-not $NoBanner)`), and banner params passed with `-NoBanner` are warned-and-ignored (the schema's `Banner` column is that list, read from the FULL schema so the runtime-only `BannerFontPath` is covered). `-BannerColor`/`-StepIcon`/`-FdColors`/`-FzfColors` stay unset (null) by default, resolved in the body via `$PSBoundParameters.ContainsKey` from the selected theme's branding, so `-Theme forestcity` alone yields the Forest City color/icon/fd-colors/fzf-colors. In the `Custom` set the body resolves color/icon from the screwcity defaults (runtime is intentionally not coupled to the custom theme). `bat` (`Enable-Bat`): `-BatTheme` is a branding-resolved sentinel (`Dracula` screwcity, `gruvbox-dark` forestcity), `-BatStyle` defaults to `numbers,changes,header`, and `-ReplaceCat` (a switch, forwarded `-ReplaceCat:$ReplaceCat`) aliases `cat`→`bat`; the wizard prompts the cat-override in the **Wiring** tree and the other two as text prompts after it — the cat-override (default **Yes**, Build emits a bare `-ReplaceCat`), then `-Message`-stable `Read-SpectreText` prompts for the theme and the style, each pre-filled with the current value (text prompts, not menus: the wizard still runs before bat is installed, so `bat --list-themes` cannot be enumerated yet). `less` (`Enable-Less`) carries **three** knobs, all forwarded: `-Options $LessOptions` (→ `$env:LESS`, default `-R -F -i`), `-SetPager:$SetPager` (→ `$env:PAGER='less'`), and `-ReplaceMore:$ReplaceMore` (→ the `more`→`less` alias). **`-SetPager` and `-ReplaceMore` were one fused switch until stage 3** and are now deliberately independent: `help` invokes the literal string `more.com`, so the alias alone never redirects it, which is precisely the case the fused switch could not express. **Migration:** an existing profile carrying only `-ReplaceMore` now gets the alias and *not* `$env:PAGER` — re-running the installer restores both, since the wiring tree seeds them together. `-LessOptions` is likewise new: the `-Options` parameter had existed and been documented on `Enable-Less` since it was written, but the orchestrator never passed it, so `$env:LESS` was effectively hardcoded — `Tests/Initialize-PwshProfile.Tests.ps1` now pins that it is passed. Unlike bat, less is still **not** themed. less runs after `fd` but has no init-time ordering constraint. `xh` (`Enable-Xh`) gained `-ReplaceHttp` (forwarded `-ReplaceHttp:$ReplaceHttp`) — it had **no parameters at all** and claimed `http`/`https` unconditionally; the aliases *and* the completer's `-CommandName 'xh', 'http'` widening now both ride that switch, exactly as `Enable-Bat` gates the `cat` widening on `-ReplaceCat` (a completion registered for `http` is meaningless without the alias). `fd` (`Enable-Fd`) and `fzf` (`Enable-Fzf`): `-FdColors` (→ `Enable-Fd -LsColors`, `$env:LS_COLORS`) and `-FzfColors` (→ `Enable-Fzf -Colors`, fzf `--color`) are branding-resolved sentinels. The fzf step is fixed-policy for most of it: `-Style 'full'`, `-Height '~100%'`, `-ProviderChord 'Ctrl+t'`/`-HistoryChord 'Ctrl+r'` (PSFzf key bindings — fzf ships none), a fixed `--ansi --ignore-case` baseline in `$env:FZF_DEFAULT_OPTS` (`--ignore-case` forces case-insensitive matching across every fzf surface, overriding fzf's default smart-case — PowerShell/Windows is case-insensitive; `Enable-Fd` likewise passes `--ignore-case` in its `$env:FZF_DEFAULT_COMMAND`, though fd is used in list-all mode so fzf does the actual matching), a constant bat `-PreviewCommand` (scoped to `$env:FZF_CTRL_T_OPTS`, the Ctrl+T widget, so it never leaks into zoxide's directory picker), and a constant `-UseFd`. **Those last two, and `Enable-Fd -IntegrateFzf`, used to be derived from co-enablement (`$enabled -contains 'Bat'`/`'Fd'`/`'Fzf'`) and are now unconditional** — every tool is present, so there is nothing to derive. Two fzf keybinding knobs **are** wizard-customizable (unlike the rest): `-GitKeyBindings:$FzfGitKeyBindings` (the Ctrl+G git chords, wizard param `-FzfGitKeyBindings`, a `[switch]` off by default/opt-in — off because lazygit covers git) and `-TabExpansionChord $FzfTabChord` (wizard param `-FzfTabChord`, default `Ctrl+Spacebar`, which Enable-Fzf also binds to `Ctrl+@`). `-Height '~100%'` is written to `$env:_PSFZF_FZF_DEFAULT_OPTS` (PSFzf's widget-only opts, read in preference to `$env:FZF_DEFAULT_OPTS`): PSFzf's PSReadLine widgets otherwise force an inline `--height=40%`, so supplying a `--height` both suppresses that default and makes the Ctrl+T/Ctrl+R/git pickers fill the shell, while `$env:FZF_DEFAULT_OPTS` stays height-free so a bare `fzf` and zoxide's `cdi` keep their alternate-screen fullscreen. `Enable-Fd` runs **after** `Enable-Fzf` so `fzf.exe` is on PATH for its `-IntegrateFzf` check; the color knobs (`-FdColors`/`-FzfColors`) are runtime-only and not threaded through the wizard, but the two fzf keybinding knobs **are** — they flow through `Get-PwshProfileDefault` (defaults `$false`/`Ctrl+Spacebar`), the Wiring step (the chords toggle in the tree, the chord as a text prompt), `Build-PwshProfileInitializeCall` (emits a bare `-FzfGitKeyBindings` only when turned on, `-FzfTabChord` only when non-default), and `Read-PwshProfileInstalledSetting` (re-run seeding).

**Install wizard (re-run aware)**: `Install-PwshProfile` is **interactive-only** — when PwshSpectreConsole prompts are unavailable it `Write-Warning`s that an interactive session is required and **makes no changes** (no degraded default write). It no longer asks *which* tools to install — every tool always runs — so its Features step became **Wiring**: a grouped checkbox tree over the binary "what does this take over?" choices, then the free-text settings a checkbox cannot express (bat's theme and style, less's options, the fzf tab chord). The toggles are one source of truth — `Private/Install/Get-PwshProfileWiringCatalog.ps1` returns `{Group;Label;Setting;On;Off;Help}` rows, and the tree, its legend, and the review panel's summary all project from it. **`On`/`Off` is a value pair rather than a boolean** because `ZoxideCommand` is a string: its checkbox means `cd` vs `z`, which is how a non-boolean setting still presents as one honest checkbox. `Tests/WiringCatalog.Tests.ps1` pins the invariants that shape depends on — labels unique across *all* groups (the Spectre prompt keys selection by label string), On≠Off, every `Setting` a real wizard-settable schema key of the matching `Kind`, and every schema default equal to the row's On or Off (a default matching neither would open unchecked and be silently rewritten). Only `ZoxideCommand` defaults to its On value; nothing else claims a command name unless asked. `Private/Install/Read-PwshProfileWiringTree.ps1` renders it, reusing the deleted feature tree's Spectre mechanics (reassign-per-extension-call, label-keyed `Select`, group header pre-checked only when every child is), and returns an answer for **every** row — an unchecked box is a real "no" that clears the setting, not a missing key. Its Spectre body is not unit-tested (the prompt throws outside an interactive terminal, and its only other branch is guarded on the prompt *type* being absent, which importing the module makes unreachable); the fold-into-settings behavior is covered through a mock in `Tests/Install-PwshProfile.Tests.ps1`. **It also installs the tool CLIs**, as one more one-time machine action alongside the Nerd Fonts / winget-settings / Windows Terminal steps — placed **after** the winget-settings step (scope and progress-bar preferences must land before installing through winget) and gated on `-not $WhatIfPreference` like the rest. It installs from the catalog's `PackageId`/`Exe` rather than by calling the `Enable-*` functions, which would also *wire* the setup session (aliasing `cat`, rebinding `cd`) mid-wizard; that split is what the catalog↔enabler anti-drift test in `Tests/ToolCatalog.Tests.ps1` exists to protect, and it is the replacement for the `ValidateSet` check lost with `-Enable`. Startup keeps its own `Invoke-Step "Install"` bodies unchanged — after a wizard run they all short-circuit on `Get-Command` (~36ms for the whole catalog), and a genuinely missing tool still installs there. **The install is visible at both ends**, because `Invoke-Step`'s nested calls only mutate the transient spinner: left alone the whole tool phase collapses to one summary line that can hide minutes of downloading. The **plan** shows in the wizard's **Winget** step — `Private/Install/Get-PwshProfileToolInventory.ps1` projects the catalog's winget rows through `Test-CommandAvailable` (**the same probe `Install-WingetPackageSafe` uses as its short-circuit**, so the list and the install agree by construction rather than coincidence) and `Private/Install/Show-PwshProfileInventory.ps1` renders them as indented rows (`✓` present, `↓` will install, `·` conditional, plus a `N present · M to install · K only if needed` count). Data and render are split so the data half is testable without a console; the review panel's `Tools:` line projects the same counts. The renderer is **generic** — any rows with a `Label` and an `Installed` — because a second inventory feeds it (below); an optional `Detail` on a row replaces "will install" with the condition under which the item is fetched, and it is read through `PSObject.Properties` so the tool rows need no such column just to satisfy StrictMode. The list covers **all thirteen packages, git and oh-my-posh included** — they were kept out of the catalog until this existed, which meant they landed on the machine unannounced at first startup. It goes in the Winget step because that step configures winget and the list is what winget will do — it *frames* the scope/progress-bar questions rather than trailing them — and because it is the earliest point the plan can be seen, the install itself happening after the review screen. **Rows, not a panel**: it draws under that step's own header panel, and `Format-SpectrePanel` would additionally need an `Out-Host` or its rendered string leaks into the caller's return value. `↓` rather than `✗` is deliberate: a tool not yet fetched on a clean machine is the expected state, not a failure, and the module has no cross glyph (its only negative marker is the bare `!` in `'! Heads up'`). The **actuals** show at apply time: `Install-PwshProfile` re-probes (several steps and the review screen sit in between, and `Install-WingetPackageSafe` patches `$env:Path` as it goes) and opens **one top-level `Invoke-Step` per package it genuinely installs** — top-level is the whole point, since a nested step writes no permanent line, which is the trap being undone. An already-present tool gets no line at all (the helper short-circuits, and nine `[ 3ms]` lines would be noise); when nothing needs fetching, one `Tools — all N already present` line whose body re-runs the short-circuit for every tool, so it carries a real elapsed time and still catches a tool that vanished since the probe. Nothing may render *inside* a running step: writing to the host while a spinner is live tears it, the hazard the `6> $null` redirections on the Windows Terminal steps exist for. **The gallery modules get their own wizard step** (`Modules`, step 3 of 7) — `Private/Startup/Get-PwshProfileModuleCatalog.ps1` names each module the profile installs on demand plus an optional `Detail`, `Private/Install/Get-PwshProfileModuleInventory.ps1` probes it with `Test-ModuleAvailable` (the same call `Import-ModuleSafe` uses to decide), and the step renders it through the shared renderer. It is **disclosure only** — nothing installs there, `Import-ModuleSafe` still does that at the point of use — so it has nothing to ask and ends on a bare `Read-SpectreText -AllowEmpty` "Press Enter to continue": every other step pauses on its own prompt, and without one the next step's header would scroll it away the instant it drew. `Tests/ModuleCatalog.Tests.ps1` walks the module's own source with the AST for every real `Import-ModuleSafe` call and asserts the two sets match **in both directions** — a call with no catalog row is an undisclosed install, a row with no call site is a promise about something never fetched. Parsed rather than grepped, because `Import-ModuleSafe Terminal-Icons` also appears in half a dozen comment-based help blocks. **Startup reports what it installed** via `$script:StartupInstall`, a list declared at the top of `Install-WingetPackageSafe.ps1` (the `Invoke-Step` module-state shape) that records a package only when an install genuinely ran *and* produced the exe; `Initialize-PwshProfile` clears it on entry and, after the WinGet step closes, emits **one** warning naming everything installed — accumulated rather than warned per package because eleven warnings on a clean install would be noise, and a warning rather than a `Write-Host` because stream 3 is the only channel `Invoke-Step` replays after the spinner clears. `Install-PwshProfile` passes **`-Quiet`** so setup, where installing *is* the expected work, never trips the notice. **The done step offers to apply the settings to the current session** rather than ending on "now run `. $PROFILE` yourself" in the one session already sitting there — a `Read-SpectreConfirm` with `-DefaultAnswer 'y'`, gated on `-not $WhatIfPreference` and on the outcome not being `BareImportPresent`. **Deliberately NOT gated on `$result.Changed`** — that was the first shape and it was wrong: the block text is only one of the things a run changes (it also installs the tool CLIs, the fonts, and the winget/Windows Terminal settings), so a re-run answering every prompt the same way writes a byte-identical block, reports `AlreadyPresent`, and lost the offer on the commonest re-run of all — the very one after which a reload matters most, since this session's `Enable-*` steps ran at startup before those tools existed. The hint text switches to say so when `Changed` is false. `BareImportPresent` is the one skipped outcome (nothing written, by design). **What it runs is `$call` — the generated `Initialize-PwshProfile` line — not `. $PROFILE`.** Dot-sourcing the file would also re-execute the *user's own* profile code, which carries no idempotency contract of its own (duplicate PATH appends, re-registered handlers, re-imported modules), to apply a change that lives entirely inside the managed block; `$call` is exactly what was just written, so it applies what changed and nothing else, and it is all code this module owns and has made reload-safe. It goes through **`Invoke-InGlobalScope`**, since invoked from a module function everything `Initialize-PwshProfile` defines would land in *that function's* scope and vanish on return; `$call` needs no escaping (module-generated text, not user input), and the call is `$null =`-suppressed because `Invoke-InGlobalScope` returns whatever the script emits, which would otherwise leak into the command's own output and break "returns nothing without `-PassThru`" (the existing `returns nothing by default` test is that guard). A failure to apply **warns instead of throwing**, deliberately against this command's "genuine errors throw" rule: the install has already succeeded, and a user's own profile code throwing must not turn a completed install into a failed one. It must not sit inside an `Invoke-Step` — the reload opens its own top-level steps. **The wiring switches are one-way in-session**, so on a re-run (`$reconfiguring`) the hint says so: `-ReplaceCat`/`-ReplaceMore`/`-SetPager` only ever *set* their alias or env var and a changed `ZoxideCommand` leaves the old name defined, so turning something on applies on reload while turning it off genuinely needs a new shell. Note also that `Install-PwshProfile`'s interactivity guard probes whether the *module* exposes `Read-SpectreSelection`, **not** whether the host is interactive — it is `$true` under Pester, so any prompt added here needs a mock in `Tests/Install-PwshProfile.Tests.ps1`'s `Describe 'Install-PwshProfile'` `BeforeEach` or the suite blocks on a real Spectre prompt. The grouped Core/WinGet feature tree, its `Read-PwshProfileFeatureTree` helper, the "(new)"-tool tagging, the `# Tools available:` snapshot comment, and `Confirm-PwshProfileEnableAll` are all **gone**. On a re-run, `Install-PwshProfile` parses the existing block via `Read-PwshProfileInstalledSetting` (a failure-tolerant AST parse of the `Initialize-PwshProfile` call) and seeds the wizard's prior choices; it returns `@{ Settings = … }`, and that single-key wrapper is deliberate — a **bare** `Initialize-PwshProfile` (everything default) parses to an *empty* settings hashtable, which is a successful read, and an unwrapped empty hashtable would be falsy and read as "unparseable" at the caller's `if ($prior)`. The wizard seeds a custom theme's branded prompts with **neutral** defaults (`Silver`, `:gear:`, and bat's `ansi`, which follows the terminal's own colors) — a custom theme has no bundled identity to inherit. **The settable-parameter set is one source of truth**: `Private/Install/Get-PwshProfileSettingSchema.ps1` returns one row per settable `Initialize-PwshProfile` parameter (`Name, Kind, Default, BrandingKey, Neutral, Tool, Banner, Emit`), and `Get-PwshProfileDefault`, `Read-PwshProfileInstalledSetting`, `Build-PwshProfileInitializeCall`, the wizard's re-seed, and `Initialize-PwshProfile`'s banner-param warn list are all projections of it — adding a settable parameter is one schema row plus its prompt, never six hand-maintained lists. `Kind` (how Read parses) and `Emit` (how Build renders) are separate axes and never derived from each other; `Emit = 'None'` marks the runtime-only parameters the wizard must never write, `Emit = 'Custom'` the three Build deliberately places by hand (the mutually exclusive `Theme`/`CustomTheme` pair and `NoBanner`'s fixed slot); **row order is the emit order**. `Kind = 'Array'` is no longer legal — the parser's array handling went away with `-Enable`, and `Tests/SettingSchema.Tests.ps1` fails an array row rather than letting it silently read back as a scalar. The `Tool` column no longer gates anything; it is kept as the record of which enabler owns each parameter, still held to real catalog tokens. `BrandingKey` names the `Get-BundledThemeBranding` member rather than assuming it equals the setting name (`FdColors` reads `LsColors`), and is what makes a theme switch re-seed *every* branded key. `Tests/SettingSchema.Tests.ps1` pins the projections against the tool catalog, the branding map, and `Initialize-PwshProfile`'s real parameter types. `Build-PwshProfileInitializeCall` emits **only** what differs from the themed defaults, so an install that customized nothing yields the bare call `Initialize-PwshProfile` (it returns that literal rather than interpolating an empty part list, which would leave a trailing space). The generated bootstrap block (`Get-PwshProfileBlock`) is the markers, a guidance comment steering users to **re-run the installer** rather than hand-edit, and the single `Initialize-PwshProfile` call — **no `Import-Module` line** (invoking `Initialize-PwshProfile` auto-loads the module; the manifest's explicit `FunctionsToExport` makes command discovery work).

**PwshSpectreConsole output gotcha**: `Write-SpectreFigletText` and the `Format-*` widgets emit their rendered ANSI string to the *pipeline* (not the console) — at a prompt the formatter prints it, but anything invoked from the `.psm1` at import time must pipe to `Out-Host` or the output is silently discarded. `Write-SpectreHost` and the live displays write to the console directly and don't need this.

**Install-wizard chrome & help-markup convention**: the `Install-PwshProfile` wizard's look is built from three `Private/Install/` helpers. `Format-PwshProfileHelpMarkup` is the **single source of truth for highlighting** — it converts a markdown-ish convention to safe Spectre markup: `**term**` → accent (`#c9aaff`, tool/product names), `` `code` `` → cyan (`#5fd7ff`, file types/commands/paths), everything else escaped (via `Get-SpectreEscapedText`) and wrapped in a body style (`grey` by default; pass `-Body default` for no wrapper). **Write help strings in this convention** anywhere they flow through `Write-PwshProfilePromptHelp` (inline `›` hint lines) or `Write-PwshProfileStepHeader` (the per-step rounded panel: `"◆ Title · N of M"` header — plain text, color from the border, Spectre trims any padding spaces — over a formatted body). Both `Format-*`/panel helpers emit to the pipeline, so `Write-PwshProfileStepHeader` pipes its panel to `Out-Host` internally (the leak the bare step calls would otherwise expose; there's a test for it). **Vertical rhythm is the helpers' job, not the caller's**: both lead with one blank line and neither trails one, so a help block is separated from the previous answer while staying welded to the prompt it explains. A step is otherwise a long run of help-then-prompt pairs that renders as an undifferentiated wall of text with no seam between one question and the next. `Write-PwshProfilePromptHelp` writes **one** blank for the whole block, not one per line — the lines inside a block are one continuous thought (and it emits nothing at all for an empty block, since callers build the array with a conditional element). The wizard threads each step's 1-based index + total into the header; `$state` carries the fixed UI colors `Accent`/`Code`, intentionally decoupled from the prompt theme being configured. Keep the wizard's `-Message` strings stable — the wizard tests key mocks on them. `Read-SpectreSelection` wraps Spectre's interactive `SelectionPrompt`, which **clears itself on submit** (no persist toggle), so the chosen value would vanish — unlike `Read-SpectreText`, which leaves its answer on screen; the wizard therefore echoes each selection (Theme/alignment/font/step icon) via `Write-PwshProfilePromptAnswer` (accent `✓` + grey value, escape-only). The glyph vocabulary is small and worth keeping so: `✓` (chosen / present), `↓` (will install, in the tool inventory), `◆` (panel headers), `•` (setting rows), `›` (help lines and the step breadcrumb), `·` (separator). **There is deliberately no `✗`** — the one place a negative was needed reads `! Heads up`, and the inventory uses `↓` rather than a cross because "not fetched yet" is a plan, not a failure. Don't advertise "leave blank" escape hatches for prompts that carry a pre-filled `-DefaultAnswer` (Enter keeps the default, not blank).

**Bundled assets live under `Assets/`** (`Assets/Themes/` for the oh-my-posh themes, `Assets/Fonts/` for FIGlet `.flf` fonts). Paths are resolved through `Private/` helpers so there's one source of truth each: `Get-BundledThemePath -Name <theme>` (in `Private/Prompt/` → `Assets/Themes/<theme>.omp.json`, default `screwcity`) and `Get-BundledFontPath -Name <font>` (in `Private/Rendering/` → `Assets/Fonts/<font>.flf`). Those helpers resolve paths off `$script:ModuleRoot` (set once at the top of the `.psm1`), **never** a per-file `$PSScriptRoot` — the same applies to `Show-PwshProfileReadme` resolving the README. This is load-bearing: `build.ps1 -Task Build` compiles the module with **ModuleBuilder** into a single `.psm1` with every function inlined, where `$PSScriptRoot` is the module root rather than the file's own folder. (`Prefix.ps1` and `Suffix.ps1` at the repo root hold the shared preamble/tail and are fed to ModuleBuilder as `-Prefix`/`-Suffix`, so the dev loader and the compiled module cannot drift.) A `Join-Path $PSScriptRoot '..' '..'` would still pass every test — the suite imports the repo tree — and break only in the published package, so always use `$script:ModuleRoot` for bundled-asset paths. The banner is rendered by the generic `Write-Figlet` (formerly `Show-ProfileBanner`): a pure figlet writer with mutually-exclusive `-Font` / `-FontPath` parameter sets, no trailing blank line, defaults of `-Font ANSIShadow` and `-Color '#c9aaff'` (the module's signature purple; note the screwcity *banner* color from `Get-BundledThemeBranding` is `#4c81c8`, and `Initialize-PwshProfile` passes that instead), and a missing-bundled-font fallback to the default font.

- **Two bundled themes, palette-only twins.** `forestcity.omp.json` is a copy of `screwcity.omp.json` with **only** the `palette` block recolored (every palette *key* name preserved, so all segment references resolve unchanged) — when editing one theme's structure, keep the other in sync, and recolor by palette values, never by rewriting segments. Validate a theme change parses as JSON and (ideally) renders. Each palette intentionally carries a **full color ramp**, so roughly half its keys are referenced by no segment — that's deliberate (it keeps the two palettes symmetric and gives a ready customization surface); don't "clean up" the unreferenced keys. The set of bundled themes is **discovered dynamically** from `Assets/Themes/*.omp.json` via `Private/Prompt/Get-BundledThemeName.ps1` (strips the `.omp.json` suffix) — there is **no hardcoded theme list**. `Initialize-PwshProfile -Theme` (parameter set `Bundled`, mutually exclusive with `-CustomTheme` in set `Custom`), `Get-OhMyPoshTheme -Theme`, and `Export-OhMyPoshTheme -Theme` validate with `[ValidateScript({ $_ -in (Get-BundledThemeName) })]` (module scope, so the private helper is reachable) and tab-complete via an `[ArgumentCompleter]` that globs `(Get-Module ScrewCitySoftware.PwshProfile).ModuleBase` (completers run in the *caller's* scope, where module-private functions are NOT visible). Each theme's **branding** — `DisplayName` (the friendly label for the wizard's theme picker), banner color, step icon, `BatTheme` (the `bat --list-themes` value driving `$env:BAT_THEME`), `LsColors` (the truecolor `LS_COLORS` spec `Enable-Fd` assigns to `$env:LS_COLORS`), `FzfColors` (the fzf `--color` spec folded into `$env:FZF_DEFAULT_OPTS`), and `TerminalScheme` (a Windows Terminal color scheme — a hashtable in settings.json `schemes` shape, hardcoded hex like LsColors/FzfColors, *not* parsed from the `.omp.json`; `Install-WindowsTerminalScheme`/`Uninstall-WindowsTerminalScheme` write/remove it in the user's settings.json, and its `name` is the `DisplayName` so it shows under that label in WT's scheme list) — lives in `Private/Prompt/Get-BundledThemeBranding.ps1`, a small explicit two-entry map with screwcity as the fallback for any unknown/custom theme. (Banner *text* is **not** here: it defaults uniformly to `$env:COMPUTERNAME`.) Both `Initialize-PwshProfile` (fills banner color/icon/bat-theme/fd-colors/fzf-colors not explicitly passed) and `Get-PwshProfileDefault -Theme` (seeds the wizard + the `Build-PwshProfileInitializeCall` comparison baseline) resolve those through it, so adding a third bundled theme means dropping a `.omp.json` **and** (if it wants its own color/icon/bat/fd/fzf/terminal-scheme identity) adding a branding entry. The Windows-Terminal-scheme install/uninstall functions live in `Public/Rendering/` (visual concern, like `Write-Figlet`), backed by `Private/Rendering/Get-WindowsTerminalSettingsPath.ps1` (locates settings.json) and `Private/Rendering/Edit-WindowsTerminalSettings.ps1` (the shared read/backup/reserialize engine — note the parse→rewrite round-trip drops JSONC comments, so it backs up to `settings.json.bak` first). (`Get-PwshProfileDefault` carries only the wizard-customizable subset — banner color/icon, bat theme — not fd/fzf colors, which are runtime-only.)

- **The accepted `-Font` set is discovered dynamically** from `Assets/Fonts/*.flf` via `Private/Rendering/Get-BundledFontName.ps1` — there is **no hardcoded font list**. `Write-Figlet`, `Show-FigletFont`, and `Initialize-PwshProfile -BannerFont` each validate `-Font` with `[ValidateScript({ $_ -in (Get-BundledFontName) })]` (runs in module scope, so the private helper is reachable) and tab-complete via an `[ArgumentCompleter]` that calls the **public** `Show-FigletFont` (completers run in the *caller's* scope, where module-private functions are NOT visible — calling the private helper there silently falls back to file completion). `Show-FigletFont` lists the names by default and renders samples under `-Preview`.
- Adding/removing a font is just dropping/deleting a `.flf` in `Assets/Fonts/` (file base name == the `-Font` value, no spaces). Not every `.flf` works under Spectre's parser: some throw on load (`Big.flf`/`Digital`/`Georgia11`) and some load but render **blank** (`Roman`). **Render-test any new font for non-empty output** — `(Write-SpectreFigletText 'Screw City' -FigletFontPath <f> | Out-String)` should have non-whitespace chars (an exception-only check is insufficient) — before committing, and record source/license in `Assets/Fonts/README.md`.

**Failure tolerance is a design rule**: nothing in this module may throw out of profile startup. Failures become `Write-Warning` + early return (see `Public/Core/Import-ModuleSafe.ps1`) or are silently skipped behind a `Get-Command` guard.
